# 目录说明

**docs.ai 用来记录跟 AI 工具的交互信息，方便跨会话保存记忆，以及历史修改和迭代。**

---

## 文档命名规范（强制）

> **今后在 `docs.ai/` 目录下新增的所有 `.md` 文档，必须严格按以下规则命名。**
> 与代码改动一一对应的「工作日志型」文档，一次代码提交对应一份命名合规的 md（或一份 a，后续追加当日改动写 b/c…）。

### 一、文件名结构

```
<类型前缀>-<YYYY>.<M>.<D>.<同日序号>.md
```

各段说明：

| 段 | 格式 | 示例 | 备注 |
|---|---|---|---|
| **类型前缀** | 8 个固定前缀之一，见下表 | `changed` / `feature` / `project` / `plan` / `bug` / `rule` / `ref` / `try` | 必须小写，用 `-` 连接后面 |
| **年份** | 4 位 | `2026` | 不可省 |
| **月** | 1~2 位，不加前导 0 | `8`（8 月）而非 `08` | 与 `plan-2026.8.19.b.md` 现有写法一致 |
| **日** | 1~2 位，不加前导 0 | `1` / `9` / `20` | 与上同 |
| **同日序号** | 小写字母 `a` / `b` / `c` …，按当日新增顺序 | `a` 当日第一份；`b` 当日第二份，以此类推 | 同一天内只写了 1 份也要写 `a`（不允许省略序号） |
| **扩展名** | `.md` | `.md` | 小写 Markdown |

**示例**：
- `changed-2026.8.20.a.md` —— 2026 年 8 月 20 日的第一份「已有功能修改」文档
- `changed-2026.8.20.b.md` —— 同日继续追加的第二份「已有功能修改」文档
- `project-2026.8.19.b.md` —— 2026 年 8 月 19 日第二份「项目级大改动」规划/落地文档
- `bug-2026.8.18.c.md` —— 2026 年 8 月 18 日第三份 Bug 修复记录

### 二、8 类前缀的语义区分

| # | 前缀 | 含义 | 典型场景（举例） | 反例（应使用别的前缀） |
|---|---|---|---|---|
| 1 | **`changed`** | 对**已有功能**的修改、优化、UI 调整；不涉及能力面的新增。 | 字号/颜色/间距等 UI 微调、把状态文字从粗体改细、封面尺寸调整、已有 NLU 阈值微调。 | ❌ 接入一个新的 CP（应 `feature`）；❌ 新开发一套 TTS 模块（应 `project`）。 |
| 2 | **`feature`** | 在**已有框架**上新增功能点；不改变项目整体架构，属于「在已铺好的轨道上加一个站点」。 | 在既有 CP 选择流程里新增**芒果TV CP**；在已有卡片体系里新增一种卡片 block；在已有的 ASR 框架里接入一个新 provider。 | ❌ 改动是 UI 外观样式（应 `changed`）；❌ 启动一个跨模块的大工程（应 `project`）。 |
| 3 | **`project`** | **项目级大改动**；跨模块/跨组件/需要多日配合的大功能，通常配套 `plan-*.md` + 多份 `changed/feature` 落地。 | 新增一个完整独立的 TTS 播报模块（需新建 asr/tts 类似级别的 module、对外 API、初始化链路）、引入新的搜索服务端对接 SDK、大改版整站视觉体系。 | ❌ 只是给某个按钮改文案（应 `changed`）；❌ 接入一个单独的 CP 源（应 `feature`）。 |
| 4 | **`plan`** | AI 写入**本次开发 / 更新计划**的预研/方案文档；是执行前的「蓝图」，代码落地完成后常对应 `project-*.md` 或若干 `changed/feature`。 | TTS 模块的选型与开发计划、某段大重构的实施步骤拆解、某个多日 Feature 的分阶段清单。 | ❌ 已落地结束、带最终结果的总结（应 `project/feature/changed`）。 |
| 5 | **`bug`** | 针对 **Bug 修复**（fix）的专项记录；必须复现问题、说明根因、给出修复方案与验证方式。 | OPD2404 设备上 16sp 文字被错误缩小（对应 ScreenMatch 限定符 sp 缩放问题）；启动崩溃 NoClassDefFoundError；网络请求偶发空指针。 | ❌ 纯粹的 UI 美观优化（应 `changed`）；❌ 功能缺失而非缺陷（应 `feature/project`）。 |
| 6 | **`rule`** | **记录本项目需要遵循的规则**；包含工程规范、编码约束、架构原则、命名规范、质量红线、资源适配规则等**所有人必须遵守**的长期规则。 | docs.ai/README.md 内的「文档命名规范」、Gradle/Manifest 架构依赖必须遵守的规则、sp 值不能在限定符目录缩放的规则、AAR 依赖 compileOnly/implementation 拆分原则、UI token 使用约定（后续若独立成文档即使用 `rule-` 前缀）。 | ❌ 某次 Bug 的修复过程记录（应 `bug`）；❌ 外系统/外部协议的参考资料（应 `ref`）。 |
| 7 | **`ref`** | **参考性 / 知识性文档**；不直接对应一次代码提交，属于「长期保存备查」的沉淀资料。 | 芒果 TV manifest 跳转协议 dump、mgtv_跳转点播播放页面协议解析、Android Overlay IME 修复方案、架构 png 图的说明。 | ❌ 本项目实际落地的一次代码修改总结（应 `changed/feature/project`）；❌ 本项目内部强制执行的规范（应 `rule`）。 |
| 8 | **`try`** | （补充）**试验 / 探路性质**；方案不确定是否被采纳、尝试后可能被废弃。 | 对某一技术方向做可行性验证、不进入主分支的草稿方案。若最终落地，其最终结论应迁移到 `changed/feature/project/bug` 对应文档中。 | ❌ 已确认采纳并落地的修改（应归入上面 1~7）。 |

### 三、命名格式的两种变体

docs.ai 下的所有 `.md` / `.txt` 文档，**必须以 8 类前缀之一 + `-` 开头**（前缀不可省略，不可混用）。按文档生命周期分为两种变体：

#### 变体 A：工作日志型（与一次代码提交强相关，强制完整版）
```
<前缀>-<YYYY>.<M>.<D>.<同日序号>.md
```
**强制适用于**：`changed` / `feature` / `project` / `plan` / `bug` / `try` 六类。示例见第一章。核心要点：
- 一次代码提交（或一次计划 / 一次 bug 修复）至少对应一份变体 A 文档。
- 同一天多份用 a/b/c… 区分，不可省略序号。

#### 变体 B：静态长期型（规则/参考沉淀，允许省略日期段）
```
<前缀>-<可读名称>[_版本].md   或   <前缀>-<可读名称>.txt
```
**仅允许用于**：`rule` / `ref` 两类——均为"长期保存备查、与单次提交弱相关"的文档，若使用日期命名会让名称迅速显得陈旧，因此使用可读名称更合理。
已按此格式重命名的示例：
| 新文件名（变体 B） | 前缀 | 内容 |
|---|---|---|
| `rule-android-project-rules_v1.0.md` | rule | 本项目工程级强制规则 v1.0 |
| `ref-ui-element-map.md` | ref | UI 元素 ID ↔ XML ↔ Kotlin 代码映射表 |
| `ref-mgtv_跳转点播播放页面.md` | ref | 芒果 TV 跳转点播播放页面协议解析 |
| `ref-android_overlay_ime_fix_for_codebuddy.md` | ref | Android Overlay/IME 问题排查沉淀 |
| `ref-mgtv_manifest_dump.txt` | ref | 芒果 TV Manifest 原始 dump |

> 若某条 `rule` 或 `ref` 文档与某次启动日期强相关（例如「2026.8.20 当日定稿的屏幕适配规则」），也可退回使用变体 A，形如 `rule-2026.8.20.a.md`。

#### 固定名豁免
| 路径 | 说明 |
|---|---|
| `README.md`（本文件） | 目录总说明 + 命名规范，固定名；内部「命名规范」章节内容本身即属 `rule` 类 |
| `artifacts/` | 图片 / 二进制附件目录，不属于文档正文，不参与前缀规范 |

> ⚠️ **重要追溯红线**：`changed / project / plan / bug / feature / try` 这 6 类的历史日志文档，一旦写入并与 Git log 中某次 commit 对应后，严禁再改名。若归档需要，可以在 `ref-` 下新建索引类文档来整理引用，但不改动原日志文件的名称。
