# plan · 安卓竖屏版适配（只给方案，未动代码）

> 类型：`plan`（变体 A：执行前的蓝图）。**本文不含代码改动**，落地时再对应产出 `project-*` / `changed-*` 归档。
> 现状基准：桌面/横屏 1280×720（`canvas_items` + `aspect=expand`），生产代码 5404 行。
> 相关背景：架构见 `docs.ai/ref-项目架构总览.md`；铁律与坑位见 `AGENTS.md`；验收数据见 `DESIGN.md`。

---

## 1. 目标与范围

**目标**：在不破坏现有桌面/横屏体验的前提下，让游戏在**安卓竖屏手机**上可玩、可读、可点。

**非目标（本期不做）**：棋盘捏合缩放、横竖屏动态切换的动画、5~6 人扩展在竖屏下的布局。

**范围**：显示与交互层（`ui/` + `project.godot` + 导出配置），**`core/` / `ai/` 一律不动**——这是分层带来的好处，规则引擎对屏幕朝向完全无感。

**仓库策略**：见 **§0**（拉分支还是开新仓库，开工前先定）。

## 0. 仓库与分支策略（建议：短期分支 + 每期合回，不开新仓库）

> 用户提问：竖屏版要动 UI，跟现有项目是什么关系——拉分支还是开新仓库？

### 0.1 先回答一个前置问题

| 问题 | 答"是"意味着 |
|---|---|
| 竖屏版要继续共享 `core/` / `ai/` 的 bug 修复吗？ | 同一仓库 |
| 会不会上架**两个** App（不同包名 / 图标）？ | **不等于**要新仓库——同一份代码 + 两个 export preset 就能出两个包 |
| 两套 UI 会长期走向不同的设计语言吗？ | 那才考虑新仓库 |
| 最终是否接受合并成"一套代码、两种朝向"？ | 同一仓库 |

### 0.2 三个选项对比

| 维度 | A 长期并行分支 | **B 短期分支 + 每期合回（推荐）** | C 新仓库 |
|---|---|---|---|
| `core`+`ai`+`game` 共享（**3057 行**，本次完全不动） | ✅ | ✅ | ❌ 复制一份，从此双份维护 |
| 20 个 `tools/` 测试脚本（3091 行）共享 | ✅ | ✅ | ❌ 复制 + 双份维护 |

| `.workbuddy/memory/` 本地踩坑笔记（**gitignore，不会跟着 clone**） | ✅ 继续在同一目录积累 | ✅ | ❌ 新目录里是空的，AI 协作记忆直接断档 |
| 导出配置 / Android 构建模板（均 gitignore） | ✅ | ✅ | ❌ 要重建第二套（含签名 keystore） |
| 桌面回归基线（(510,360)、46/24/56/18/36/51 条断言） | 分支上跑即可 | 每期合回前跑 | ❌ 新仓库要重建整套基线 |
| 长期维护成本 | ❌ 分歧久了基本无法合并 | ✅ 每期就合，冲突小 | ❌ 两份代码各自漂移 |
| 仓库体积 | +增量 | +增量 | +36M（其中 `.git` 16M）且历史独立 |

### 0.3 为什么"同仓库"是自然选择：改动的远小于共用的

| 类别 | 行数 | 本次 |
|---|---|---|
| `core/` + `ai/` + `game/` | 3057 | **不动** |
| `tools/` | 3091 | 基本不动（新增 2 个脚本） |
| `ui/` | 2247 | 部分改（布局算式 + 控件排布） |
| `project.godot` | ~30 | 改几行 |

更关键的是：**竖屏改造的本质是"给已有的静态布局算式加一个朝向参数"，不是重写 UI**。
`BoardView.board_origin_for()` 和 `HUD.content_rect()` 已经是静态纯函数，加 `portrait` 分支即可；
棋盘手绘、命中测试、规则、AI 全部原样复用。这种情况下拆仓库，等于为 20% 的改动复制 100% 的资产。

### 0.4 推荐方案的具体做法

1. **先把当前未提交的文档提交掉**（`docs.ai/ref-项目架构总览.md` + 本 plan + README 速查表），再拉分支——避免文档改动混进竖屏分支。
2. 从 `main` 拉 **`portrait`**（或 `feat/portrait-ui`）。**寿命以"期"为单位**：P0~P4 每期结束就合回一次 `main`，不要让它变成长期并行分支。
3. **每期合回 `main` 的门槛**：§8 验收清单全绿，尤其 `test_safe_area.gd` 的桌面棋盘原点仍为 **(510, 360)**。
4. 合回用 `--no-ff`，保留"竖屏这一批改动"的可回溯节点。
5. **全程只有一个代码库**；将来真要上架两个包，用两个 export preset（不同包名 / 图标 / 朝向）从同一份代码导出。

```bash
git switch -c portrait
# …P0~P4 每期若干 commit，每期末跑 §8…
git switch main && git merge --no-ff portrait -m "竖屏：第 N 期 …"
```

### 0.5 什么时候才该开新仓库

只在这几种情况下才考虑：

- 竖屏版要交给第三方做，且不想给出 `core/` / `ai/` 的源码；
- 两套 UI 确认长期分道扬镳（不同交互范式、不同美术体系），合并已无意义；
- 需要完全不同的发布节奏与版本线。

⚠️ **别用 submodule 共享 `core/`**：Godot 项目里这会带来 `.godot` 导入缓存、`class_name` 全局注册、以及 `res://` 路径全部变化的连锁问题，得不偿失。

## 2. 结论先行（TL;DR）

0. **仓库：拉短期分支 `portrait`，每期合回 `main`，不开新仓库**（对比与理由见 §0）。
1. **必须换"竖屏设计基准"**（推荐 720×1280），只改布局不够。原因是 `aspect=expand` 在竖屏下会把画面**缩小**到 0.84 倍，字和按钮比桌面还小（见 §3.2）。
2. **竖屏 = 上下分区，不是左右分栏**。棋盘在上（约占屏高 45~55%），信息与操作在下。
3. **新增一个统一的 `ui/layout.gd`**：把"当前朝向 / 逻辑基准 / 棋盘矩形 / 面板矩形"做成**静态纯函数**，供 `BoardView` 与 `HUD` 共用，并配 headless 单测。不要让 `if portrait` 散落到两个大文件里。
4. **桌面 1280×720 必须逐像素不变**——`test_safe_area` / `test_legend` / `test_ports` / `test_interaction` 的现有基线一条都不能破，这是本项目的硬规矩。
5. **Android 三件小事别漏**：`orientation` 改成竖屏（默认横屏）、返回键关弹窗、软键盘避让种子输入框。

## 3. 现状盘点：为什么现在这套只适合 PC / 横屏

### 3.1 布局契约里有三个"横向"假设

| 位置 | 现状 | 竖屏下的问题 |
|---|---|---|
| `HUD.PANEL_W = 384`（`ui/hud.gd`） | 面板钉**视口右缘**，底色铺满整列高度 | 竖屏"右缘一列"会让棋盘只剩一条竖缝 |
| `BoardView.board_origin_for()`（`ui/board_view.gd`） | 棋盘在「视口宽 − `HUD.PANEL_W` − 安全区」这块区域居中 | 竖屏下这块区域变成"窄而极高"，棋盘悬在中间、上下大片空白 |
| `HUD.content_rect()` | `vp.x - PANEL_W + 14`，内容高 = 视口高 − 24 | 竖屏下内容区被拉成一条 2857px 的长条，日志吃掉全部空间 |

三者都是**静态纯函数**（为了 headless 可测），改造时这点要保住。

### 3.2 缩放：竖屏会被**缩小** 0.84 倍（最关键的一条）

`canvas_items` + `expand` 的行为是"短边对齐设计分辨率、长边溢出"。以 1080×2400 的手机为例：

| 朝向 | 窗口 | 逻辑视口 | 逻辑→物理缩放 |
|---|---|---|---|
| 桌面 | 1280×720 | 1280×720 | **1.00** |
| 手机横屏 | 2400×1080 | 1600×720 | **1.50**（放大，舒服） |
| 手机竖屏 | 1080×2400 | 1280×**2857** | **0.84（缩小！）** |

竖屏时短边是屏幕**宽度** 1080，要塞进设计宽 1280 → 整体缩到 0.84。后果：

- 12px 的日志字 → 10 物理像素（≈0.6mm），基本读不了；
- 触控目标同步缩小；
- 视口高度 2857 让所有"按高度伸缩"的容器失控。

> ⚠️ 这一条决定了：**只改布局（方案 A）救不了竖屏**，必须同时改缩放基准。

### 3.3 触控相关

- 命中半径 `PICK_VERTEX_R = 0.40`（≈25 逻辑 px，按手指定）是按桌面 62 px/unit 调的，竖屏棋盘放大后要重新验算。
- `BoardView._unhandled_input` 只处理 `InputEventMouseMotion` / `InputEventMouseButton`：依赖 Android 的 `emulate_mouse_from_touch`（默认开）。**hover 高亮在触屏上没有意义**，`InputEventMouseMotion` 会持续触发 → 白耗电、还可能留下"粘住的高亮"。
- 弹窗宽度写死：`_center_card(width = 320)`；竖屏基准下 320 只占屏宽 44%，且资源按钮的横向排布会挤。
- 图例"?"按钮 `HELP_R = 17`（逻辑 px），缩小 0.84 后 ≈14 物理 px，偏小。

### 3.4 打包

- 仓库里**没有 `export_presets.cfg`**（且已 gitignore，正确——含签名）。
- `project.godot` 未设 `display/window/handheld/orientation`，Godot 默认**横屏** → 竖屏必须显式设置。
- 渲染器已是 `gl_compatibility`、ETC2/ASTC 已开、开屏图标已备（见 git log `8bfa146`）——这三样不用改。

## 4. 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 只改布局** | 保持 1280×720 基准，给 `board_origin_for` / `content_rect` 加竖屏分支 | 改动最小，桌面基线天然不动 | **不解决缩放**：UI 物理尺寸比桌面还小，触控与可读性不达标。❌ 单独不可行 |
| **B. 切竖屏基准** | 竖屏时把内容基准改成 **720×1280**（运行时 `Window.content_scale_size` / `content_scale_factor`），布局分支跟着走 | 逻辑→物理回到 **1.5× 放大**，字与按钮达标；基准尺寸是安卓主流（360dp×640dp @2x） | 需要接受"两套基准"，所有 UI 常量要按基准分档 |
| **C. 竖屏专用场景** | 另做 `main_portrait.tscn` + 一套竖屏 HUD | 两边互不干扰、可各自优化 | 两套 UI 会出现"改了横屏忘了竖屏"，与本项目"界面与批量共用一条路径"的精神冲突；除非 UI 彻底重写，否则不划算 |

**推荐：B 为主 + A 为辅**（B 提供正确的缩放，A 提供正确的分区布局），并通过一个统一的 `ui/layout.gd` 把两套基准的差异收敛在一处。

## 5. 推荐方案详述

### 5.1 朝向与基准

| 项 | 建议值 | 说明 |
|---|---|---|
| `display/window/handheld/orientation` | **Portrait** | 默认 Landscape，必须改。本期建议**锁定竖屏**，不处理转屏 |
| 竖屏内容基准 | **720×1280**（9:16） | 19.5:9 / 20:9 的长屏由 `expand` 把高度补到 ~1560，上下多出来的留给棋盘与日志 |
| 切换时机 | 启动时按 `vp.x < vp.y` 判定，只判一次 | 转屏支持放到后续；真要支持，就走 `size_changed` 重算并重排 |

> 落地前**先写一个 5 行的探针脚本**，在真机上打印 `get_viewport_rect()`、`get_window().content_scale_size`、`content_scale_factor`、`DisplayServer.window_get_size()`、`screen_get_dpi()`。
> 这几个值在不同引擎版本/机型上的表现有出入，先量再定，别照抄网上结论。

### 5.2 竖屏分区（720×1280 基准，首版建议值）

```
┌──────────────────────────────┐  ← 状态栏 / 挖孔（安全区上边）
│ ① 顶部状态条       h≈64      │  第 N 轮 · 骰子 · 当前是谁 · 「?」图例按钮
├──────────────────────────────┤
│                              │
│  ② 棋盘区                    │  可用 ≈ 688 × 620
│     棋盘自适应填满           │  px_per_unit 按可用区算（见 5.3）
│     （含港口牌外扩留白）     │
│                              │
├──────────────────────────────┤
│ ③ 玩家区           h≈96      │  4 位玩家压成 2×2 网格（或一行 4 张小卡）
├──────────────────────────────┤
│ ④ 操作区           h≈56      │  「掷骰子」「结束回合」「买发展卡」「兑换」
├──────────────────────────────┤
│ ⑤ 状态提示         h≈44      │  一句话提示当前该干什么（可两行）
├──────────────────────────────┤
│ ⑥ 日志（可折叠）   h≈200     │  默认展开 200，点标题栏抽屉式拉到半屏
├──────────────────────────────┤
│ ⑦ 底部安全区       h≈24~34   │  手势条，不摆任何可点控件
└──────────────────────────────┘
```

- **日志必须可折叠**：竖屏竖向空间是硬约束，常驻日志会把棋盘挤没。折叠状态建议跨局记住（不做存档也行，先只在本局内保持）。
- **玩家区压缩**：现在 4 行 × ~56px = 224 高，竖屏改成 2×2 网格（≈96~110）。
- ① 与 ⑦ 的高度**取安全区实测值**，不写死。

### 5.3 棋盘缩放公式（替代写死的 62）

棋盘含角点的包围盒 ≈ **8.66 × 8.00** 世界单位；港口牌再外推 `PORT_OUT 0.46` + 牌箱半宽 ≈ 0.16 → 需要按 **9.90 × 9.24** 单位留白。

建议（沿用静态纯函数的形式）：

```
board_rect = 分区② 扣掉四边安全区/边距
px_per_unit = min(board_rect.w / 9.90, board_rect.h / 9.24) * 0.98
```

- 720 基准、可用区 688×620 → `min(69.5, 67.1) × 0.98 ≈ 65.8`，与桌面 62 同一量级。
  **别误以为竖屏要把 px_per_unit 调很大**——真正让画面变大的 §5.1 的基准缩放（1.5×），棋盘只是"填满可用区"。
- `px_per_unit` 从 `@export 常量` 变成"由布局算出"，桌面下算出来必须**仍旧是 62**（否则截图基线全废）。建议保留 `@export` 作为手动覆写，默认走自动。

### 5.4 HUD 改造点（按文件）

| 文件 | 现在 | 竖屏建议 |
|---|---|---|
| `ui/hud.gd` `PANEL_W = 384` | 右侧定宽列 | 竖屏改"底部块"：宽 = 视口宽，高 = 分区③④⑤⑥ 之和；底色铺到左右边，内容按安全区内缩 |
| `ui/hud.gd` `content_rect()` | `vp.x - PANEL_W + 14 …` | 加 `portrait` 分支；**保持静态纯函数**以便单测 |
| `ui/hud.gd` `_apply_layout()` | 钉右缘 | 按 `Layout` 返回的矩形摆放；分隔线 `_sep` 竖屏时改横条 |
| `ui/hud.gd` `_center_card(width=320)` / `_new_dialog(width)` | 写死 320 | 改成 `min(vp.x - 2*margin, 520)`；资源按钮由一排 5 个改 2 列网格或纵向列表 |
| `ui/hud.gd` 日志 `custom_minimum_size.y = 150` | 常驻 | 竖屏下给"折叠态高度"与"展开态高度"两档 |
| `ui/hud.gd` 玩家行 `_make_player_row` | 4 行竖排 | 竖屏 2×2（用 `GridContainer`，列数按朝向给） |
| `ui/hud.gd` 种子输入框 | `LineEdit` | 软键盘弹出会盖住下半屏 → 建议移到弹窗**上半部**，或改成"随机 / 数字按钮"两种入口 |

### 5.5 新增 `ui/layout.gd`（强烈建议）

把朝向判定与所有布局算式收敛到一个 `RefCounted`（延续"静态纯函数 + headless 可测"的铁律）：

- `is_portrait(vp) -> bool`
- `content_scale_for(vp) -> Vector2i`（横屏 1280×720 / 竖屏 720×1280）
- `board_rect(vp, ins, has_log_open) -> Rect2`
- `panel_rect(vp, ins, log_open) -> Rect2`
- `px_per_unit_for(rect) -> float`

`BoardView` 与 `HUD` 都只调它，不再各自算 `PANEL_W`。这样"桌面逐像素不变"只需要在这个文件里守住一处。

### 5.6 触控与 Android 生命周期

| 项 | 建议 |
|---|---|
| hover | `OS.has_feature("mobile")` 时跳过 `_update_hover` / 鼠标移动分支——触屏没有悬停，省电也避免"高亮粘住" |
| 最小点击目标 | ≥ 48 逻辑 px（720 基准下 = 72 物理 px ≈ 12mm）；`HELP_R` 相应上调到 20~22 |
| 命中半径 | `PICK_VERTEX_R = 0.40` 是**世界单位**，随 `px_per_unit` 自动缩放，本身不用改；但要给 `test_pick.gd` 补一组"竖屏基准"用例（棋盘变大后手指定尺寸不能想当然） |
| 误触 | 落子是"点击即生效"，建议加"按下与抬起位移 < 阈值才算点击"（`InputEventScreenDrag` / 拖动距离判定），避免滑动时误建 |
| 返回键 | Android 返回键必须能关掉三类弹窗（重开 / 兑换 / 发展卡），否则玩家被卡住。走 `InputEventKey(KEY_BACK)` 或 `NOTIFICATION_WM_GO_BACK_REQUEST`；无弹窗时退出游戏要有二次确认 |
| 沉浸模式 | 导出预设里开 `screen/immersive_mode`，配合已有的 `SafeArea` 处理状态栏/手势条 |
| 软键盘 | 种子输入聚焦时把弹窗整体上移（或改用数字按钮），避免键盘盖住输入框 |

### 5.7 性能与渲染

- 渲染器 `gl_compatibility` + ETC2/ASTC 已开，手机端合适，**不用改**。
- 静态棋盘走 `_draw()`，只在 `queue_redraw()` 后重绘；关掉移动端 hover 后，帧数会明显下降（hover 每次移动都重绘）。
- 建议把 `application/run/max_fps` 显式设成 **60**（避免部分机型跑满 120 白耗电）。
- 首版**不建议**做捏合缩放/拖动平移：会给 `BoardView` 引入相机变换，命中测试要整体改坐标换算（当前 `_pick_*` 全部基于 `board_origin` 固定原点）。若确实需要，作为独立的一期做。

### 5.8 打包配置（首次）

| 项 | 建议 |

## 6. 分期落地（建议顺序）

> 每一期都应能独立跑通并回归，不要一次性大改。
> 分支策略：在 `portrait` 分支上开发，**每期末验收通过就合回 `main`**（见 §0.4），避免长期并行分支。

### P0 — 探针与基准（半天）

- **产出**：一张"本机实测值"表，作为后续所有数字的依据。

### P1 — 引入 `ui/layout.gd` + 竖屏基准切换

- 新增 `ui/layout.gd`（§5.5），`BoardView` / `HUD` 改调它。
- 启动时按朝向设置内容基准。
- **验收**：桌面 1280×720 下 `test_safe_area.gd`（棋盘原点仍 (510,360)）、`test_legend.gd`、`test_ports.gd` 全绿；新增 `tools/test_layout.gd` 断言桌面与"注入竖屏视口"两种情形的矩形。

### P2 — 竖屏分区布局

- `HUD` 面板由"右侧列"变"底部块"，玩家区 2×2、日志可折叠。
- `BoardView` 棋盘矩形与 `px_per_unit` 按 §5.3 自适应。
- **验收**：新增 `tools/shot_portrait.gd`（注入竖屏视口 + 手机竖屏安全区，走真实渲染器出图，禁止 headless——见 AGENTS.md trap 4）；配合 `tools/crop_shot.gd` 放大看 20px 级细节。

### P3 — 触控与 Android 细节

- **验收**：`test_pick.gd` 补竖屏基准用例；真机上"点图例不建村"、"返回键关弹窗"两条人工用例。

## 7. 风险与待你拍板的问题

| # | 问题 | 影响 | 我的倾向 |
|---|---|---|---|
| 1 | 只做竖屏锁定，还是支持横竖屏切换？ | 支持切换 = 布局要能热重排 + 转屏测试量翻倍 | **先锁竖屏**；转屏留到 P3 之后 |
