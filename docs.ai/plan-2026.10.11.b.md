## 1. 目标 / 非目标

**目标**：同一份代码，在安卓竖屏手机上可玩、可读、可点。分区为「**上方棋盘 + 下方玩家信息**」，日志收进按钮 + 弹窗。

**非目标（本期不做，鸣叔 2026-10-11 已拍板）**：横竖屏热切换（**锁定竖屏**，见 Q1）、4:3 平板竖屏的体验保障（**不考虑 iPad**，能跑不崩即可，见 Q2）、捏合缩放 / 拖动平移棋盘、5~6 人扩展的竖屏布局、村庄/道路动画。

**范围**：`ui/` + `project.godot` + 新增 `tools/` 脚本。**`core/` / `ai/` / `game/` 一行不动**——分层的收益在这里兑现：规则引擎对屏幕朝向完全无感。

## 2. 结论先行（TL;DR）

1. **两块分区**：上棋盘 / 下信息，不是左右分栏。隔离线上方的事（`?` 图例按钮、命中测试）一行不改。
2. **竖屏基准 720×1280**。1080×2400 手机上逻辑→物理 **1.5× 放大**，12px 的字变成 18 物理 px（現横屏只有 12），这才是"能读"的关键。
3. **新增 `ui/layout.gd`**，把朝向判定 + 全部矩形算式收进去（静态纯函数，配 headless 单测）。
4. **桌面保持 62 不动**，`px_per_unit` 自动公式只走竖屏分支（见 M1）。
5. 好消息：主流 16:9~20:9 安卓机全部算出同一个 `px_per_unit = 66.1`，**一套截图基线覆盖全部机型**（见 §3.3）。
6. `PICK_VERTEX_R = 0.40` **不用改**——它是世界单位，px 变大后热区自动从 25px 涨到 26.4 逻辑 px（≈5.0mm 直径），而相邻顶点间距 6.3mm 已经卡住上限了。
7. **朝向在启动时锁定一次**（`Layout.is_portrait()`），运行中拉伸窗口不会在两套分支间乱跳——竖屏预览的正确姿势是**启动时就用竖窗口**（见 §4.1 启动流程）。

## 3. 实测数据（本节数字全部实算，非估算）

### 3.1 棋盘外接矩形（世界单位）

用六边形几何离线实算（19 格 pointy-top，axial 中心 `(√3(q+r/2), 1.5r)`）：

| 项 | 值 |
|---|---|
| 19 格外接矩形 | **8.6603 × 8.0000** |
| + 海岸带 `COAST_BAND 0.07` | 8.8003 × 8.1400 |
| + 港口牌外推（`PORT_OUT 0.46` + 半牌 0.16）| **9.9003 × 9.2400** |

→ 沿用这两个数作为 `BOARD_W_U / BOARD_H_U`。**宽比高大 7%**，所以竖屏下瓶颈永远是**屏幕宽度**，不是高度。

### 3.2 分区算式（建议写法）

```
ins      = SafeArea.insets()                  # 手机上 18 / 34 / 18 / 18（含 MIN_* 兜底）
avail_y  = vp.y - ins.y - ins.w
ui_h     = clampf(vp.y * UI_RATIO, UI_MIN, UI_MAX)     # 0.48 / 400 / 940
board_z  = Rect2(ins.x + PAD, ins.y + PAD,
                 vp.x - ins.x - ins.z - 2*PAD,
                 avail_y - ui_h - PAD - GAP)           # PAD=8, GAP=12
px       = min(board_z.w / 9.9003, board_z.h / 9.2400) * 0.98
origin   = board_z.get_center()                        # 竖屏下 BOARD_X_BIAS 不再叠加
panel_r  = Rect2(0, board_z 底 + GAP, vp.x, vp.y - board_z 底 - GAP)
```

> `UI_RATIO = 0.48` 的由来：横屏面板内容（去掉日志后）自然高约 300，竖屏下按 1.5~2 倍排布需要 450~600；
> 0.48 保证主流机 UI 块落在 **614~768**，同时棋盘区仍有 ≥594（1080×1920 最紧机型），两头都够用。

### 3.3 各机型实算结果

| 机型 | 逻辑 vp | 缩放 | UI 块高 | 棋盘区 | `px_per_unit` | 棋盘实尺寸 |
|---|---|---|---|---|---|---|
| 桌面 1280×720（旧分支）| 1280×720 | 1.00 | — | — | **62.0（硬编码）**| 613.8×572.9 |
| 1080×2400（20:9）| 720×1600 | 1.50 | 768 | 668×760 | **66.1**（宽限）| 655×611 |
| 1080×2340（19.5:9）| 720×1560 | 1.50 | 749 | 668×739 | **66.1**（宽限）| 655×611 |
| 1440×3200（20:9）| 720×1600 | 2.00 | 768 | 668×760 | **66.1**（宽限）| 655×611 |
| 720×1520（入门机）| 720×1520 | 1.00 | 730 | 668×718 | **66.1**（宽限）| 655×611 |
| 1080×1920（16:9）| 720×1280 | 1.50 | 614 | 668×594 | **63.0**（高限）| 623×582 |
| iPad 1536×2048（3:4）| 720×960 | 2.13 | 461 | 668×427 | 45.3（高限）| 449×419 |

**三条结论**：

- **16:9 ~ 20:9 全部落在 `px = 66.1`**（受限于屏幕宽度），棋盘尺寸逐列一致 → 截图/命中测试只需一套基线。这是本节最值钱的发现。
- 1080×1920 是唯一"高度瓶颈"的主流机型，`px=63` 仍 ≥ 桌面 62，**不比桌面差**。
- iPad 竖屏 `px=45.3` 明显偏小。**Q2 已拍板不照顾**：竖屏体验只对 16:9 及更长的屏幕负责；4:3 平板不追求好看，靠 §4.4 的 ScrollContainer 保证**能跑不崩**即可。

### 3.4 触控验算（1080×2400，≈400 ppi）

| 项 | 逻辑 px | 物理 px | 物理尺寸 |
|---|---|---|---|
| 顶点热区**直径**（`0.40 × 2`）| 52.9 | 79.3 | **5.04 mm** |
| 相邻顶点**间距**（1.00 u）| 66.1 | 99.2 | **6.30 mm** |

→ 热区直径已占顶点间距的 80%。`PICK_VERTEX_R = 0.50` 时相邻热区**恰好相切**，再大就重叠——触屏上根本无法区分两个可建村点；而 0.40 在竖屏下已有 5.04mm，够用。所以**既无需上调，也不能上调**。这条回答了 a §5.6 "竖屏要重新验算"的疑虑。

## 4. 改动清单（按文件）

### 4.1 `ui/layout.gd`（**新增**）

延续"静态纯函数 + headless 可测"的铁律，把两套朝向的差异收敛在一处：

| 函数 / 常数 | 返回 | 说明 |
|---|---|---|
| `is_portrait() -> bool` | **锁定值**（见下"启动流程"）| 唯一判定入口；测试用 `set_portrait(bool)` 注入——与 `SafeArea.set_override` 同一模式 |
| `content_scale_for(portrait) -> Vector2i` | 横屏 `1280×720` / 竖屏 `720×1280` | 启动时一次性设置 |
| `BOARD_W_U / BOARD_H_U / FIT / PAD / GAP / UI_RATIO / UI_MIN / UI_MAX` | const | §3.1~§3.2 的全部常数放这里，**不允许散落到另两个文件** |
| `board_rect(vp, ins) -> Rect2` | 棋盘分区 | 内部再分 `board_origin_for` / `px_per_unit_for` |
| `px_per_unit_for(bz) -> float` | `min(w/9.9003, h/9.2400) * 0.98` | **桌面分支不调它**（见 M1） |
| `panel_rect(vp, ins) -> Rect2` | 信息区（含铺到屏边的部分）| 横屏 = 右侧 `PANEL_W` 列；竖屏 = 底部块 |
| `content_rect(vp, ins) -> Rect2` | 面板**内容**区 | 现有 `HUD.content_rect()` 迁过来再加分支 |
| `dialog_width(vp) -> float` | `minf(vp.x - 2*24, 560)` | 替代写死的 320 |

`BoardView` 与 `HUD` 只调它，**不再各自算 `PANEL_W`**。

#### 启动流程（审核补：这是 Q1"锁竖屏"的落地语义）

```
BoardView._ready()（场景树里最先 _ready 的相关节点，且在 ui/ 内、不动 game/）：
  1. ⚠️ portrait = DisplayServer.window_get_size().x < .y      # 读【窗口物理尺寸】！
     #              不能读 get_viewport_rect()：见下面 R8，启动那一刻视口还没同步
  2. Layout.set_portrait(portrait)                  # 锁定，之后不再变
  3. get_window().content_scale_size = Layout.content_scale_for(portrait)
  4. → 触发 size_changed → BoardView/HUD 的布局函数用【新 vp】自适应重排
```

验算过这条流程在三种启动方式下都自洽（**前两行已由 P0 探针实测证实**，见 §5 P0）：

| 启动方式 | 初始 vp（基准未切）| 判定 | 切基准后 vp |
|---|---|---|---|
| 桌面 1280×720 窗口 | **1280×720**（实测）| 横 | 1280×720（**不变，基线安全**）|
| 手机 1080×2400 | 1280×2857（scale 0.84）| 竖 | **720×1600**（scale 1.5）|
| 桌面 `--resolution 720x1280`（竖屏预览）| **1280×2275**（实测，scale 0.5625；原推算 2276 舍入差 1）| 竖 | **720×1280**（scale 1.0）|

三条推论：

- **朝向必须锁定在启动时**，不能每次布局都拿 `vp` 现判：否则桌面用户把窗口从横拉成竖，会在两套分支间乱跳，而那时基准没换，vp 是 1280×2276 这种怪尺寸——布局能算但完全没意义，还引入不可测状态。锁定后，运行中拉伸窗口永远走横屏分支，与现状（`size_changed → _fit_to_viewport` 自适应）完全一致。
- **桌面竖屏预览 = 启动时窗口就是竖的**（`--resolution 720x1280`）。⚠️ AGENTS.md trap 3 的教训照搬过来：竖屏下涉鼠标坐标的测试/截图，窗口尺寸必须与竖屏基准一致（720×1280），否则合成事件会点偏；并且**必须在基准切换后的下一帧**再截图（`_ready` 里同步读到的还是旧 vp）。
- headless 单测里 `Layout` 默认值 = `false`（横屏），现有全部基线测试零影响；需要竖屏用例时 `set_portrait(true)` 注入。

### 4.2 `ui/board_view.gd`（改动小）

| 位置 | 改法 |
|---|---|
| `@export var px_per_unit` | **默认值 62.0 不动，也不引入 `-1` 哨兵**。竖屏时由 `_fit_to_viewport()` 把算出的值**直接写回这个成员**；横屏永不覆写 |
| `board_origin_for(vp, ins)` | 委托 `Layout`；**桌面路径必须逐字节回到现在的算式**（`(left+right)*0.5 + BOARD_X_BIAS`），否则 (510,360) 基线崩 |
| `_fit_to_viewport()` | 竖屏时额外写入 `px_per_unit` |
| `_draw()` 首行海色 | 保留铺满视口——底部会被 HUD 面板盖住，无需裁剪 |
| `help_center()` / `legend_rect()` | **不改**。竖屏下左上角仍在棋盘区左上角，图例（约 300×230）也放得下 668×760 的棋盘区 |
| `_ready()` 开头 | 调上面 §4.1 的启动流程 |

> 为什么不用 `-1 = 自动` 哨兵：`tools/test_ports.gd`、`tools/shot_help.gd`、`tools/screenshot.gd` 都在**读写这个成员**。哨兵会引入"export 值 / 运行时值"两个真源；而"竖屏覆写、横屏不动"只有一个真源，现有脚本（全部跑横屏）读到的永远是 62，零影响。

### 4.3 `ui/hud.gd`（改动的主体）

结构上的好消息：**同一棵 `_box` VBoxContainer，从"右侧 384 宽的列"变成"底部 720 宽、`ui_h` 高的块"即可**，内部顺序完全不动，比横屏还宽了 84%。

| 位置 | 改法 |
|---|---|
| `_apply_layout()` | 按 `Layout.panel_rect / content_rect` 摆 `_bg` / `_sep` / `_box`；竖屏把 `_sep` 从竖条（1.5 宽）改成横条（1.5 高） |
| `_build()` 日志部分 | `_log` 从 `_box` 里**移出**，挂到新的日志弹窗；原地补一个「查看日志（N 条）」按钮 |
| **新增** `_log_dlg` | 复用 `_new_dialog()` 骨架 + 关闭按钮，卡内 `RichTextLabel` 撑满 ~80% 屏高 |
| `set_log()` | 保留"全量 + 底部吸附"逻辑不变；**弹窗打开时**强制滚到底（关闭态无所谓） |
| `_log_title` | 改写按钮文字：`事件日志（N）` |
| `_unhandled_input` 弹窗链 | 日志弹窗作为**第六层**并入现有五层链（`_dlg` → yop → mono → dev → trade → log）：Esc / Android 返回键关最上层，行为与现有弹窗一致 |
| `_center_card(w=320)` / `_new_dialog(w)` | 调 `Layout.dialog_width(vp)` |
| `_status` / `_dice` / 按钮 | 竖屏加 `custom_minimum_size.y`（建议 44~76，P2 实测校准） |
| `_act_row`（掷骰/结束/买/兑换）| 668 宽横排放得下，**不改** |
| `PANEL_W` | 保留（仍服务于横屏分支）|

### 4.4 信息区高度不够时的兜底

按 §3.3，UI 块在主流机型有 614~768 高，但内容自然高度**要等实测**（玩家行横屏是 ~28，放大后仍未定）。两道保险：

1. **弹性分配**：给"玩家卡"和"状态提示"挂 `SIZE_EXPAND_FILL`，多余空间由它们吃掉，不留纯空白；
2. **ScrollContainer 兜底**：`_box` 外层包一层（同位置同尺寸，只开竖向），iPad 那种 461 高的极端情形可滚，不会内容溢出屏幕。

> ⚠️ ScrollContainer 内不能再有 `SIZE_EXPAND_FILL` 占满的容器，否则撑不起来——P2 落地时要实测一下再定谁吃掉空间。这条写进 AGENTS.md traps。

### 4.7 触控与 Android 细节

| 项 | 做法 |
|---|---|
| **hover** | `OS.has_feature("mobile")` 时在 `_unhandled_input` 里跳过 `InputEventMouseMotion` 分支（含 `_update_hover`）。触屏没有悬停，每次移动全量重绘纯粹白耗电，还会留下"粘住的高亮" |
| 最小点击目标 | ≥ 48 逻辑 px（@720 基准 = 72 物理 px ≈ 12mm）；`HELP_R` 17 → 竖屏 22 |
| 误触 | 按下到抬起位移 > 10 物理 px 判为滑动，不当点击 |
| **返回键** | 与 Esc 同一处理：关**六层弹窗链**（§4.3）的最上层；走 `_notification(NOTIFICATION_WM_GO_BACK_REQUEST)` 或 `KEY_BACK`；无弹窗时退出给二次确认 |
| 软键盘 | 种子输入框聚焦时整体上移，或改成"随机/沿用"两个快捷按钮为主（已有实现里它俩就在，只是还要能提交手打值）|

## 8. 审核记录

> **2026-10-11 15:17 复审**（鸣叔拍板 Q1/Q2/Q3 之后，全文重新过了一遍）。本节记录审核中发现并已修正的问题，落地时不用再踩：

| # | 发现 | 修正 |
|---|---|---|
| **R1** | 原稿 `is_portrait(vp)` 每次布局现判朝向 → 桌面运行中拉伸窗口会在两套分支间乱跳，且那时基准未换，vp 是 1280×2276 之类的怪尺寸，引入**不可测状态** | 改为**启动时锁定**（§4.1 启动流程），`set_portrait(bool)` 注入测试——与 `SafeArea.set_override` 既有模式一致 |
| **R2** | 原稿 `px_per_unit` 用 `-1 = 自动` 哨兵 → export 值与运行时值**两个真源**，`test_ports.gd` / `shot_help.gd` / `screenshot.gd` 读到哪个全看时机 | 改为**竖屏覆写成员、横屏永不覆写**（§4.2），单一真源，现有脚本零影响 |
| **R3** | 原稿没写"谁在什么时候设 `content_scale_size`"，而 `game/` 一行不动的约束排除了 GameDirector | 落在 `BoardView._ready()`（场景树顺序最早、且在 `ui/` 内），并补了三种启动方式的验算表（§4.1）|
| **R4** | 原稿没意识到 AGENTS.md **trap 3** 对竖屏同样成立：竖屏截图/鼠标测试的窗口尺寸必须等于竖屏基准（720×1280），且要等基准切换后的下一帧 | 写进 §4.1 推论与 §5 P2 验收；桌面竖屏预览姿势 = `--resolution 720x1280` **启动时**就给竖窗口 |
| **R5** | 日志弹窗只写了"新增"，没提它要进 `_unhandled_input` 的 Esc/返回键链 | 补为**第六层**（§4.3），与现有五层（重开 → 丰收 → 垄断 → 选卡 → 兑换）行为一致 |
| **R6** | `PICK_VERTEX_R=0.50 相切"彻底分不开"`表述不准：0.50 恰好相切、>0.50 才重叠 | 精确化（§3.4），结论不变：既无需上调也不能上调 |
| **R7** | 若干笔误：§0.2 M2 残留英文、§2"干净消息"、§4.6"72 0基线"、§4.7 hover 行表格列错位 | 已全部修正 |
| **R8** | **视口尺寸在启动时还没就绪**（P0 探针实测）：`SceneTree._initialize()` 里读 `root.get_visible_rect()` 得到 **1280×1280**（不是 1280×720，换算倍率 0.5625），而 `DisplayServer.window_get_size()` 那时已经是对的 1280×720。等一帧 `process_frame` 后视口才同步 | 启动流程的**朝向判定改用窗口物理尺寸**（§4.1 第 1 步），不能读 `get_viewport_rect()`——否则 `_ready` 时可能读到未同步的 vp 而误判。`probe_display.gd` 里已加 `await process_frame` 并写了原因 |

**审核后仍留意的两个点**（不修，落地时验证）：

- `Layout` 的 static 状态在 headless 批量跑（`sim_runner` 同时起多个场景？不会——它不开 UI）里只有单实例，无并发问题；
- **P0 已量到一半**：视口尺寸启动后要等一帧才就绪（R8）。**P1 还要量另一半**：`content_scale_size` 改完后 `size_changed` 何时触发、新 vp 在第几帧生效——用 `test_layout.gd` + `probe_display.gd` 的等帧版本钉死，不靠推理。
